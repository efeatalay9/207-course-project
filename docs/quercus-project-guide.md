## Project overview and teamwork

The project is 20% of the course grade before the individual adjustment. The team develops a Java Swing desktop app, iterates in lab and outside lab, and presents and demonstrates the result. Course staff assess the product, its specification, and the team's ability to explain the design and show collaborative development. The project domain and scope require approval from a member of the course team. Ask for early scope feedback in lab, on Piazza, or via the course's AI tutor. [Team project hub](https://q.utoronto.ca/courses/444184/pages/team-project) · [Overview](https://q.utoronto.ca/courses/444184/pages/project-overview) · [Project expectations](https://q.utoronto.ca/courses/444184/pages/project-expectations) · [Sample user stories and scope approval](https://q.utoronto.ca/courses/444184/pages/project-domains-and-sample-user-stories)

The Week 5 ideas actually list **Course Scheduler** under Education & Learning. The list offers brainstorming examples, and a member of the course team still approves the team's scope. For this team, that discussion should cover which official-builder workflows are in the demo and which complete path each member owns. The original plan is for five people using basic Java, with one or two distinct feature contributions each. The course asks each member to implement at least one complete story and lead at least one MVP use case. [Developing user stories](https://q.utoronto.ca/courses/444184/pages/developing-project-user-stories) · [Week 5 project ideas](https://q.utoronto.ca/courses/444184/pages/project-ideas-from-week-5-user-stories-shared-in-class) · [AI tutor for scope](https://q.utoronto.ca/courses/444184/pages/discuss-the-scope-of-your-project-with-an-ai-tutor)

Team Formation says members register in the same tutorial and join the same Quercus group. Room assignments can differ before teams form. For the team contract, agree on communication, meetings, review practices, decision-making and disputes using observable, specific commitments. The course instructs all members to approve the contract branch's PR and add their names to `TeamContract.md`. The sample's two-reviewer norm is an option for ordinary team PRs. ## Lab 7 and Milestone 1

Lab 7 is in the **Week 8** module, November 9 or 10. Finish the blueprint milestone by **Friday, November 13**.

- Agree on and record the user stories, each case's owning member, which use cases are in the MVP, and sufficient extra cases to explain the product. The blueprint calls for at least two domain entities, with their fields and relevant methods. Include links to API documentation, tell the reader how each service helps, and record whether the team has called it successfully. Include the key design. Start work on the entities, UI and interactors, and record tasks in GitHub Issues or a similar tracker.
- **Show the TA a sketch of the main UI elements.** For each important case, draw the relevant before and after states, the control the actor uses, and useful alternate paths, such as no results or an API failure. Pencil, text, or a design tool can work. The prepared Swing sketch shows how search, the course plan, and the weekly grid are connected. Ask the teammates and TA to review those flows. [Draft sketches](ui-sketches.md)
- Choose candidate entities based on the actor's goals. Walk through which class owns each step and which runtime objects exchange messages. Sketch a class diagram for types and relationships and a sequence diagram for the runtime messages. Nail down the view's expected data before wiring the presenter and controller. A listener on the view triggers the request, and the view can subscribe to view-model changes to display the new state.
- Leave time for both integration and error handling. Develop an interactor with a test fake while the real UI and data source are still being prepared. Discuss where the API needs actual responses and where a small fixture can give the team a reproducible demo.

## Lab 8 and Milestone 2

Lab 8 is in the **Week 9** module, November 16 or 17. Finish the working prototype milestone by **Friday, November 20**.

- **One team member submits the project's GitHub repository URL to the MarkUs `GroupProject` assignment.** Confirm the recorded status with the teammate who submitted it.
- Work through the project and individual rubrics and agree with the TA on the subset to demonstrate by the end of this lab or the following lab. Each member should be able to run and explain the work they completed.
- Each member submits a substantial project PR and reviews at least one teammate's PR. Make the useful change and its evidence clear in the description. Review behaviour, tests, style and Javadoc, Clean Architecture, SOLID, and whether the PR is easy to review. Track reviews as well as authorship. [Timetable PR workflow and examples](code-review.md)
- Run at least one end-to-end app use case and actual calls to the external services the team has selected. Keep a short response example and the UI result. Use a fixture for repeatability and alternate outcomes.
- For the next use case, describe preconditions, success and extensions, and decide what travels over the input and output boundaries. Write the interactor with an in-memory gateway and test recorder first. Then wire the action listener, controller, presenter, and view-model display. [Implementation checklist](project-expectations.md#how-to-implement-a-use-case)

## Testing and persistence examples posted November 23

Lab 9 links back to the **Week 8** testing lecture (`08-CA.pdf`). A unit test calls a real entity or interactor with small input and stand-ins for storage and the presenter. Integration tests exercise the actual adapter against controlled storage or an endpoint. A system test drives a full wired interaction from view to output. The November 23 examples say automated end-to-end UI tests are optional for project teams. Combined automated unit and integration tests and a manual Swing demo can cover the different layers. [Testing lecture](https://q.utoronto.ca/courses/444184/files/45915260?wrap=1) · [November 23 storage and testing examples](https://q.utoronto.ca/courses/444184/pages/sample-code-for-external-data-storage-and-testing-examples)

The course's `ca-login` `db-user` branch demonstrates data access through a hosted Java-accessible service. Its DAO uses GET `/user?username=…`, GET `/checkIfUserExists?username=…`, and POST or PUT `/user` as appropriate on the documented host. The newer NoteApplication example shows a note can be retrieved by name, while edits require its password. Its project also demonstrates a Checkstyle setup and test separation. Use those examples to learn adapters and persistence. Keep private profile data in the timetable's local store. For an explicit share, send only the necessary timetable snapshot. ## API selection and verification

Start with documented service functionality the project needs and a small real Java request. Check access and cost, credentials, response shape, request limits, connectivity, and rules for using or reusing the response. Separate read-only test calls, fixture tests and deliberate data writes. Hoppscotch or Postman can inspect an endpoint. Record the date and result of a real call from the Java app for presentation evidence. Mapping services may have different endpoints and licensing for location data, maps, and routing. Batch/cache where appropriate. [API Advice](https://q.utoronto.ca/courses/444184/pages/api-advice) · [API resources](https://q.utoronto.ca/courses/444184/pages/api-resources)

The Java app uses the public Timetable Builder for the course catalogue. For the presentation, demonstrate fetching results for a selected term and division and keep dated evidence of the successful call. Prerequisite rules come from a separate file, and the student profile remains local. Local file save/open can satisfy persistence. [Project blueprint API guidance](https://q.utoronto.ca/courses/444184/pages/project-readme-and-minimum-viable-product-mvp) · [Timetable API plan](implementation-guide.md#catalogue-ingestion-and-search)

The course suggests the optional Clean Architecture Visualizer (CAVE). Its examples run `npm install -g clean-architecture-visualizer@latest`, then `cave verify` or `cave start` from the repo. CAVE discovers common course-style directories under `src/main/java` such as `app`, `data_access`, `entity`, `interface_adapter`, `use_case` with case-specific subfolders, and `view`. The team uses Java names such as `domain` and `usecase` and has its own compiled dependency test. Check actual imports and boundaries in either tool's findings. ## How Weeks 7–10 lecture material applies

| --- | --- |
| Week 7 post-lecture notes | High-level timetable rules depend on narrow inputs they own. File/HTTP mechanisms implement those interfaces. Dependency inversion also applies to the output boundary and presenter. Use case and entity classes can stay free of UI classes. |
| Week 8 post-lecture notes and testing slides | Draw objects and call paths through an interaction and show where the request, entity and response are created. Main or an AppBuilder wires concrete dependencies. Use fake ports for unit tests and actual adapters for a separate integration test. |

Test negative outcomes, check code quality, and finish the outputs agreed with the TA. |
